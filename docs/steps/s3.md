# S3 · 任务 CRUD + SQLite + MOCK 引擎

## 这一步做了什么

把 S1/S2 的"前端演示数据"换成真实链路：提交需求 → 服务端建任务入队 → MOCK 引擎写产物到 `workspace/{task_id}/` → 扫描产物落库 → 前端轮询看状态推进 → iframe 预览可交互产物。刷新页面、重启进程都不丢。

新增 / 修改：

| 文件 | 作用 |
|---|---|
| `app/config.py` | 环境变量集中读取（`MOCK_ENGINE` / `TASK_TIMEOUT` / `MAX_CONCURRENCY` / `DATA_DIR` / `WORKSPACE_DIR` / 体积上限），只读 dataclass，改配置走重启 |
| `app/models.py` | 表 DDL、状态机常量、`Task` / `Artifact` 数据类、产物类型映射 |
| `app/db.py` | SQLite 封装：单连接 + WAL、建表与只增迁移、状态写入、事件与产物读写 |
| `app/engine/base.py` | `Engine` Protocol：`run(task_id, prompt, workdir, emit)` |
| `app/engine/mock_engine.py` | MOCK 引擎：写固定可交互页面，`asyncio.sleep` 模拟三阶段 |
| `app/tasks.py` | 编排层：信号量、超时、取消、启动清理、`scan_artifacts` 产物扫描、路径穿越防护 |
| `app/api.py` | 新增 `/api/generate`、`/api/tasks`、`/api/tasks/{id}`、`/cancel`、`/preview`、`/files/{path}` |
| `app/main.py` | 启动时建目录、初始化数据库、把残留任务收尾；关闭时取消在跑任务 |
| `app/__init__.py` | 版本 `0.3.0`、`STEP = "s3"` |
| `web/app.js` | 全部改为 fetch 真实接口 + 1.5s 轮询；提交后乐观插入 pending 卡片；失败态与重试 |
| `web/index.html` | 版本 chip 与帮助面板改为 S3 说明；补上取消按钮；内联 SVG favicon |

## 数据模型

```sql
tasks(id PK, parent_id, prompt, status, stage, error, workdir, created_at, updated_at)
artifacts(id PK, task_id, path, kind, size, created_at)
task_events(id PK, task_id, seq, message, created_at)
```

- `PRAGMA journal_mode=WAL` + `synchronous=NORMAL`；单写连接，所有访问都在同一事件循环线程内，避免写锁。
- **只增不改**：`db._migrate()` 只做 `ALTER TABLE tasks ADD COLUMN parent_id`，不删列、不改类型，任意历史 tag 都能启动。
- 启动钩子把残留 `pending` / `running` 统一置为 `failed`（`interrupted by restart`），避免刷新后看到永远转圈的任务。

## 关键实现点

- **终态不可回退由 SQL 保证**：`UPDATE ... WHERE status NOT IN ('succeeded','failed','cancelled')`，返回值告诉调用方这次写入是否生效（取消与成功收尾的竞态靠它判定）。
- **并发 1**：`asyncio.Semaphore(MAX_CONCURRENCY)`，排队期间任务保持 `pending` 且可取消；进入临界区前再确认一次状态，防止"已取消又被置为 running"。
- **超时**：`asyncio.wait_for(..., TASK_TIMEOUT=600)`，超时后协程被取消并记为 `failed`。
- **引擎可替换**：`tasks.get_engine()` 只在这里决定用 MOCK 还是真实引擎；`app/` 顶层不 import metagpt，S3 在没有 MetaGPT 的环境（含 Python 3.14 本地）也能完整跑通。
- **阶段上报尽力而为**：`emit` 内部吞掉数据库异常并记 warning，避免 DB 抖动把已有产物的任务判失败。
- **产物由扫描器解释**：`scan_artifacts()` 递归收集文件，跳过隐藏目录 / `node_modules` / `__pycache__`，单文件超 5MB 跳过、单任务累计超 50MB 直接判失败；入口优先级 `index.html` → `Index.html` → 路径最短的 `*.html`；没有 HTML 则 `failed(no previewable artifact)`。
- **预览隔离**：iframe `sandbox="allow-scripts"`（无 `allow-same-origin`），产物响应带 CSP，生成代码拿不到主站 Cookie。
- **路径穿越防护**：`/files/{path}` 对 `Path.resolve()` 后的路径校验前缀仍在 `workspace/{task_id}/` 内，越界与不存在都返回 404，不泄露是否存在。
- **毫秒时间戳**：`created_at/updated_at/events.created_at` 用毫秒精度，前端才能把阶段耗时算成 `0.5s / 1.5s / 0.4s` 而不是全 `0.0s`。
- **轮询容错**：连续 4 次请求失败才停止轮询并提示，单次网络抖动继续重试。

## 怎么部署

S3 不增加依赖，`requirements.txt` 基础段照旧（fastapi / uvicorn），升级只需拉代码重启：

```bash
cd ~/atoms-dev-demo
git pull
bash scripts/deploy.sh          # git pull + 同步依赖 + 覆盖 unit + 重启 + 探活
```

首次启动会自动创建 `data/`（SQLite 文件）与 `workspace/`，不需要手工建库，也不需要执行任何迁移脚本。默认 `MOCK_ENGINE=1`；如需切真实引擎，见 S4。

运行期产物：

```
data/app.db          # 任务与事件（WAL 模式，另有 -wal/-shm）
workspace/{task_id}/ # 每次生成的产物，失败也保留
logs/app.log         # 2MB × 3 滚动
```

## 怎么验收

```bash
bash scripts/verify_s3.sh                 # 本机
TARGET=public bash scripts/verify_s3.sh   # 公网（先在 deploy/verify.env 配好 PUBLIC_BASE_URL）
```

脚本幂等，每次跑都新建两条任务（一条跑到成功、一条立即取消），共 **28 项**检查：

- 服务身份：`/health` 可用、`step` 不低于 s3、`engine` 非 unavailable
- 建任务：返回 `task_id`，`accept_ms < 200`
- 状态机：推进到 `succeeded`、最终 `stage=checking`、事件流含 planning/coding/checking
- 产物：`artifacts` 含 html、`entry=index.html`、`index.html`/`styles.css`/`app.js` 可下载
- 预览：`/preview` 200 + `text/html` + CSP 头 + 内容含 `<!doctype html`
- 安全：`../` 与 URL 编码的穿越都被拒绝、不存在任务 404
- 持久化：任务出现在列表；**更早的任务仍可读取**（重跑一次本脚本即可覆盖，或重启服务后再跑）
- 取消：立刻取消得到 `cancelled`，且 0.5s 后状态没有被引擎改回 `running/failed`

人工确认（真实浏览器，S3 收尾时已用本地 Chromium 走通）：

1. 打开地址 → 顶栏 `后端已连接 · S3`、`引擎 MOCK`，任务列表显示历史任务
2. 点示例标签「待办清单」→ 输入框被填充 → 点「生成应用」
3. 立即看到新任务为「排队中」，随后阶段卡片依次点亮，耗时约 `0.5s / 1.5s / 0.4s`，标签变成「全部阶段完成」
4. 右侧预览加载 MOCK 产物：点击 `+` 计数从 0 变 2、点「切换配色」变浅色 → 证明沙箱内脚本可执行
5. 点左上「取消」出现在运行中任务的阶段标题旁；取消后状态为「已取消」，预览显示「任务已取消」空态
6. 切换列表里的历史任务 → 预览与阶段卡片随之切换，任务 ID 显示在右侧工具栏
7. 刷新页面 → 任务与预览仍在（`GET /api/tasks` 走的是 SQLite）
8. 窗口压到 900px → 上下堆叠，预览区高 540px（60vh），无横向滚动

## 已知限制与设计偏差

| 项 | 说明 | 处理 |
|---|---|---|
| `GET /api/tasks/{id}/events`（SSE） | design 标为可选，本步只做轮询；事件已落 `task_events`，随时可加 | 不阻塞，S6 前不实现 |
| 外键 `REFERENCES` / `ON DELETE CASCADE` | 建表未加外键约束，删除由 `db.delete_task()` 手工级联 | 单写连接 + 无对外删除接口，行为等价；避免中途改 DDL 导致新旧库 schema 漂移 |
| 超时与无产物的 error 文案 | 实际为 `timeout after 600s`、`NoPreviewArtifact: 产物中没有 HTML，无法预览` | 比 design 的字面值更可读，前端直接展示给用户 |
| 启动清理范围 | design 只要求清理 `running`，实现同时清理 `pending` | 排队中的任务在进程退出后已无协程接手，不清理会永远挂起 |
| 产物超 50MB | 直接判任务失败，`artifacts` 表为空（目录保留） | design 未定义该路径；宁可失败也不写半份数据 |
| 验收脚本产生垃圾任务 | 每次运行新建 2 条 `验收任务：…` | 便于识别；量级小，不影响演示 |
| 前端预览 URL | 用 `/files/{entry}` 而非 `/preview` | 相对资源（`styles.css`）能正确解析；两者都带 CSP |
