# S5 · 继续修改与版本历史

## 这一步做了什么

到 S4 为止用户只能"从头生成"。这一步补上 Atoms 最核心的迭代体验：在某次结果上继续提需求，生成新版本，并能随时切回历史版本查看它的产物。

| 文件 | 变化 |
|---|---|
| `app/db.py` | 新增 `root_of()`（沿 `parent_id` 找根）与 `list_versions()`（按版本树广度优先 + 时间升序） |
| `app/api.py` | 新增 `GET /api/tasks/{id}/versions`；`/api/generate` 继续复用已有 `parent_id` 字段 |
| `web/index.html` | 需求区增加「继续修改」与修改态提示；新增「版本链」区块 |
| `web/app.js` | 修改态状态机、版本链渲染、版本切换预览、任务列表 vN 标记 |
| `web/styles.css` | 版本 chip、修改提示、`[hidden]` 兜底（修掉 flex 容器无视 hidden 的老问题） |
| `scripts/verify_s5.sh` | 22 项验收，自建 v1→v2→v3 链，不依赖历史数据 |

## 数据与接口

版本链不建新表，沿用 S3 的 `tasks.parent_id`：

- 一次"继续修改" = 新建一条任务，`parent_id` 指向被修改的版本；
- 旧版本的任务行与 `workspace/{task_id}/` 产物都不动，所以"回滚预览"只是换个任务看，不写库；
- 同一版本被修改两次会形成分支，`list_versions()` 用广度优先 + `created_at` 拍平成 v1…vN（时间最早的在前）。

```http
GET /api/tasks/{id}/versions
```
```json
{
  "root_id": "t_20261118_165228_d15d",
  "current_id": "t_20261118_165519_9cbb",
  "total": 5,
  "versions": [
    {"id": "t_...", "parent_id": null, "status": "succeeded", "artifact_count": 4, "...": "..."}
  ]
}
```

`versions` 用的是任务摘要结构（与 `/api/tasks` 一致），带 `artifact_count`，前端用它显示 vN 与状态。

## 前端交互

- **继续修改**：仅当当前任务 `succeeded` 时可用。点击后输入框下方出现「将基于 v3 生成新版本」提示，提交按钮文案变成「生成新版本」；提交时带上 `parent_id`。
- **版本链**：只在该任务有 2 个以上版本时出现，chip 显示 `v1…vN`，当前版本高亮；点击 chip 即切到那个版本的预览，旧产物照常可看。
- **任务列表**：属于同一条链的任务在标题前加 `vN` 标记，便于对照。
- **失败保护**：提交失败（例如父任务被删）不清除修改态，用户改完可以再试；切换任务、点「重试」都会清空修改目标，避免误挂到别的版本上。
- **新增版本即时可见**：提交后立刻把 pending 的新版本插进版本链，进入终态时再刷新一次，避免"提交后链里没有 v4"的空窗。

## 怎么部署

无新增依赖、无数据库迁移（`parent_id` 在 S3 建表时已存在），直接覆盖代码重启：

```bash
cd ~/atoms-dev-demo
git pull
bash scripts/deploy.sh
curl -s localhost:8000/health   # 期望 "step":"s5"
```

## 怎么验收

```bash
bash scripts/verify_s5.sh                 # 本机
TARGET=public bash scripts/verify_s5.sh   # 公网
```

22 项检查（脚本自己造 v1→v2→v3，不复用历史数据）：

- 步骤号 ≥ s5
- v1 建立并生成成功；v2 带 `parent_id=v1`、`v2.parent_id` 回指 v1；v3 基于 v2
- `/versions` 可用、`root_id` 指向 v1、`total=3`、三个 id 都在列表里、v1 排第一
- 从中间版本 v2 查询时 `root_id` 仍是 v1、`current_id` 是 v2
- v1/v2/v3 的 `/preview` 都返回 200；v1 的 HTML 里仍是 v1 自己的需求（末版本没有覆盖旧产物）
- `parent_id` 不存在返回 404 且带 `parent task not found`
- 不存在任务的 `/versions` 返回 404
- 独立任务（无 parent）的版本链只有 1 个版本

浏览器人工确认（本步已用 playwright-cli + 本地 Chromium 走通，截图在 `logs/shots/s5-*.png`，不入库）：

1. 选中链尾任务 → 左侧出现「版本链 共 5 个版本」，chip 高亮当前版本
2. 点「继续修改」→ 提示「将基于 v5 生成新版本」，按钮变「生成新版本」
3. 输入修改需求并提交 → 约 2.5s 后版本链变成 6 个 chip，任务列表出现带 `v6` 标记的新行
4. 点 `v1` → 右侧预览切回 v1 的产物（工具栏任务 ID 同步变化），iframe 内仍是 v1 的内容
5. 选中只有 1 个版本的任务 → 版本链区块自动隐藏
6. 控制台 0 error

## 怎么回滚

```bash
git checkout s4 && bash scripts/deploy.sh
```

数据库里多出来的 `parent_id` 值对 S4 无影响（S4 读该列但不展示版本链）；产物目录也不需要清理。

## 已知限制

| 项 | 说明 |
|---|---|
| 分支展示 | 同一版本被改两次会形成分支，前端按时间拍平成一条线，不画树；演示场景够用 |
| 版本数量上限 | `list_versions()` 一次最多扫 200 条任务；超出后老链可能查不全，属于演示规模假设 |
| 删除版本 | 未提供删除接口，历史版本只增不删（与"产物保留"的取舍一致） |
| 修改失败重试 | 目前是"重新提交一次"，不自动复用上次的 prompt；父任务被删会直接报 404 |
| 版本命名 | 只有自动编号 `v1…vN`，不支持自定义名称或备注 |
