# S2 · FastAPI 接管（/health + 静态托管）

## 这一步做了什么

把 S1 的 `python3 -m http.server` 换成 uvicorn，让 `app.main:app` 成为唯一入口：注册 `/health`、挂载 `web/`、写启动/停止日志。页面视觉不变，但顶栏状态灯改为读 `/health` 的真实返回，用来肉眼确认「后端真的接管了」。

新增 / 修改：

| 文件 | 作用 |
|---|---|
| `app/__init__.py` | 包标记，集中放 `__version__` 与 `STEP`；注释里写明**顶层不得 import metagpt** |
| `app/api.py` | 路由层，目前只有 `GET/HEAD /health` |
| `app/main.py` | 入口：日志配置、路由注册、`web/` 静态挂载、lifespan 启停钩子 |
| `requirements.txt` | 基础依赖（fastapi / uvicorn）与引擎依赖（metagpt）分段，S2/S3 只装基础段 |
| `deploy/atoms.service` | `ExecStart` 改为 `.venv/bin/uvicorn app.main:app --workers 1` |
| `scripts/verify_s2.sh` | 本步验收脚本（15 项） |
| `web/index.html`、`web/app.js`、`web/styles.css` | 顶栏状态灯由 `/health` 驱动，探测中琥珀 / 在线绿 / 离线灰 |
| `scripts/deploy.sh` | `uv pip install` 显式指定 `--python .venv/bin/python`，避免未激活 venv 时报错 |

## 关键实现点

- **`/health` 同时注册 HEAD**：运维习惯用 `curl -I` 看状态码，只注册 GET 会返回 404。响应体字段：`status/version/step/engine/uptime_s/python/time`。
- **静态挂载顺序**：先 `include_router`，再 `app.mount("/", StaticFiles(html=True))`，保证 `/health`、以后的 `/api/*` 优先于静态文件匹配。
- **日志用标准库而非 loguru**：`logs/app.log`（2MB × 3 滚动）+ stdout 交给 journald，不额外引入依赖。`design.md` 里写的是 loguru，这里按"减少依赖"取舍，行为一致。
- **单 worker 写死在 unit 里**：S3 起任务队列与并发信号量都在进程内，多 worker 会让状态分裂。
- **前端探测失败不报错**：`fetch('/health')` 超时 2.5s，失败只把状态灯变灰（例如仍用 S1 的 `http.server` 打开页面时），页面仍可演示。

## 怎么部署

服务器首次升级到 S2，需要先有 venv 与基础依赖（`deploy.sh` 不会替你创建 venv）：

```bash
cd ~/atoms-dev-demo
git pull

# 首次：建 3.11 环境（S2 用系统 3.12 也能跑，但 S4 要 3.11，直接建 3.11 免得重建）
uv python install 3.11
uv venv --python 3.11 .venv
uv pip install --python .venv/bin/python -r requirements.txt

# 部署（更新 unit -> 重启 -> 探活）
bash scripts/deploy.sh
```

`deploy.sh` 做的事：有上游就 `git pull` → `.venv` 存在就按 `requirements.txt` 同步依赖 → 覆盖 `/etc/systemd/system/atoms.service` → `daemon-reload` + `enable` + `restart` → 探测 `/` 直到 200。

## 怎么验收

```bash
bash scripts/verify_s2.sh                 # 本机
TARGET=public bash scripts/verify_s2.sh   # 公网（先在 deploy/verify.env 配好 PUBLIC_BASE_URL）
```

脚本检查 15 项：`/health` 200、`status/step/version/uptime_s` 字段、HEAD 可用、响应头 `server: uvicorn`、首页与 `styles.css`/`app.js` 可访问、`app.js` 含 `probeHealth`、`/api/tasks` 返回 404（路由未被静态托管吞掉）。

人工确认（真实浏览器）：

1. 打开 `http://<地址>:8000`，顶栏状态灯应为**绿色**，文案 `FastAPI 已接管 · S2`，版本 chip 显示 `s2`
2. 停掉服务再刷新页面：状态灯变灰、文案改成「离线演示」，页面仍可操作（内置演示数据）
3. 打开 `http://<地址>:8000/health` 直接看到 JSON
4. 打开 `http://<地址>:8000/api/docs` 能看到 OpenAPI 文档

## 怎么回滚

```bash
cd ~/atoms-dev-demo
git checkout s1
# 恢复 S1 的静态服务 unit 后重启
sudo cp deploy/atoms.service /etc/systemd/system/atoms.service
sudo systemctl daemon-reload && sudo systemctl restart atoms
```

S2 没有数据库与运行时状态，回滚只需换代码 + 换 unit，`.venv` 可以留着不影响 S1 的 `http.server`。

## 已知限制（留给后续步骤）

| 限制 | 在哪一步解决 |
|---|---|
| 页面仍是内置演示数据，提交只在浏览器里模拟 | S3（SQLite + 真实接口 + 轮询） |
| 没有任务接口，`/api/tasks` 返回 404 | S3 |
| 静态资源无缓存头、无 CSP | S6 |
| `engine` 字段恒为 `none` | S3（mock）/ S4（metagpt） |
| 日志无 request id，只有启停与业务日志 | 不解决，单机单用户场景够用 |
