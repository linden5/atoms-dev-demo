# S10：迭代修复走旧代码 + 自检功能走查（生成管线修复）

## 背景

S8 验收暴露的三个管线问题（见 `out/pipline.md` 工作包），其中存储禁用已在 S9 解决，
本步解决剩余两个：

1. **迭代修复是盲重写**：引擎看不到父版本代码，用户说"修复 XX"时走全新生成，同一 bug 复现；
2. **自检发现不了逻辑 bug**：REVIEW_PROMPT 六项全是结构性检查，无功能走查；
   "2+3 判表达式无效"这类校验误拦无法被静态阅读发现。

## 改了什么

| 文件 | 内容 |
|---|---|
| `app/engine/prompts.py` | CODE_PROMPT 新增第 7 条（代表性输入走查调用链，占位符条目顺延为第 8）；REVIEW_PROMPT 换 8 项清单（新增沙箱约束与功能正确性），输出加 `verified` 字段；FIX_PROMPT 约束行补存储禁令；新增 `REVISION_PROMPT`（旧代码 + 反馈 → 改稿，先定位根因、禁止重构换风格） |
| `app/engine/html_utils.py` | 新增 `storage_hits()`：正则列出 localStorage/sessionStorage/document.cookie 出现位置，供自检修正（`window.__ATOMS__` 存储桥不受影响） |
| `app/engine/llm_engine.py` | `run()` 新增 `parent_html` / `requirement` 可选参数：`parent_html` 非空走 `_revise()`（REVISION_PROMPT，跳过 planning，两次不合格才抛错）；`_review()` 改返回 `(issues, review_status, verified)`，本地体检三条硬问题（外链/占位符/存储）**先于模型意见且不受模型 `ok=true` 影响**；`meta.json` 新增 `review_status`（ok/parse_failed/call_failed）与 `verified_interactions` |
| `app/engine/base.py` | `Engine.run` 协议新增可选参数 `parent_html` / `requirement`（向后兼容，非 LLM 引擎忽略） |
| `app/engine/mock_engine.py` / `metagpt_engine.py` | `run` 签名同步（参数忽略），契约不变 |
| `app/tasks.py` | `start()` 建任务时读父版本入口 HTML（`_parent_html`），>60KB 时 `_slim_parent_html` 只瘦身 `<script>` 之前的注释与空白（逻辑代码绝不截断）；父版本产物缺失退回全新生成并记 warning；`requirement` 传用户本轮原话。`start_turn()` 接入**提示词指定版本**（`_resolve_parent_by_prompt`）：规则先行（`planner.parse_version_ref`，vN/第N版/上一版），疑似语义指代再走一次 LLM 兜底（`llm_engine.resolve_version_by_llm`，输出约束防幻构，失败回退最新版），命中即从该版本分叉 |
| `app/__init__.py` | `STEP = "s10"` |
| `scripts/verify_s9.sh` | step 断言从 `= s9` 放宽为 `>= s9`（与 verify_s8 的 `>= 8` 同款写法；步骤号继续推进，验收语义不变） |
| `docs/design.md` | 4.3 新增「迭代修复（revision 分支）」与「自检与体检（S10 强化）」两段 |

`app/planner.py` 不动：revision 分支直接用父版本 HTML + 用户原话，`build_prompt` 的
历史拼接只在全新生成时使用。

## 怎么部署

```bash
git pull && ./scripts/deploy.sh && sudo systemctl restart atoms
TARGET=public bash scripts/verify_s8.sh   # 公网回归
```

无 schema 变更，无需迁移。

## 怎么回滚

`git checkout s9` 重启即可。`review_status` / `verified_interactions` 是 meta.json 新字段，
旧代码不读取，无副作用。

## 验收

本地回归（fake LLM，2026-11-19）：

```bash
python scripts/fake_llm.py --port 8099 --scenario success &
ENGINE_MODE=llm LLM_BASE_URL=http://127.0.0.1:8099/v1 LLM_MODEL=fake LLM_API_KEY=dummy LLM_CACHE=0 \
  python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 &
bash scripts/verify_s8.sh   # 38 通过 / 0 失败 / 1 跳过
bash scripts/verify_s9.sh   # 15 通过 / 0 失败 / 1 跳过（STEP=s10 下复验）
```

- 第二轮任务走 REVISION 分支：meta `brief=""`、coding 步骤 tokens 明显变大（含父版本 HTML）、
  版本链 parent 正确；
- `_review` 的 `parse_failed` / `call_failed` 路径 L0 单测通过；
- `_slim_parent_html` 不动 `<script>`（含 JS 内 `<!--` 字符串）、`storage_hits` 不误伤 `__ATOMS__`。

真模型下待人工验证：生成计算器 → 反馈"2+3 报表达式无效" → 新版本在旧代码上修复且计算正确；
生成记账工具 → 不再出现 localStorage、界面不承诺刷新保留（S9 后持久化走 `__ATOMS__` 存储桥）。

## 边界与后续

- 编排层只在 `parent_id` 存在且父版本产物可读时走 revision；跨版本链"从历史版本另开分支"
  同样生效（parent 即所选版本）。
- 提示词指定版本（P2，用户点名要的）：规则 11 例 + 真实链定位 3 例 + LLM 兜底 4 例 L0 全过。
  已知误判边界：需求正文里出现 vN 字样（"支持 v1 v2 两个视图"）会被当版本引用，
  概率低，不做意图消歧；LLM 兜底只在规则未命中且文本含指代词（那版/恢复/回到等）时触发，
  单独一次调用（约 200 tokens 输出上限），失败静默回退最新版。
- 父版本 HTML 与用户原话都进 prompt：token 消耗上升（单次生成约多一个页面长度），
  属预期成本，靠缓存兜底重复修复场景。
- `Engine.run` 的 `steps` 在共享引擎实例上跨任务累积，是既有展示 quirk（meta 只反映
  到该任务完成时为止），未在本步处理。
